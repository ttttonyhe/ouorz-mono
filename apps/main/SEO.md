# Search and AI discoverability for lipeng.ac

## Scope

The final implementation follows the owner's instruction to preserve the original appearance and visible copy. It adds no page, profile text, language switch, navigation control, FAQ, or visual redesign. The existing CAD 20,000 scholarship edit is preserved. Research recommendations that require visible changes are not applied.

These changes are local and have not been published. The five supplied reports remain unchanged at the repository root. Their findings are recorded in the appendix as a pre-change baseline, not a claim that every scanner recommendation was implemented.

## Failure modes checked

1. Names and profiles can identify different people. The metadata uses the Waterloo affiliation, the existing Scholar identifier, reciprocal GitHub link, and linked ORCID to distinguish this researcher from namesakes.
2. A shared canonical can collapse every page onto the homepage. The route resolver derives each canonical from the actual page record, without tracking queries.
3. Content can exist only after JavaScript runs. Initial HTML was checked, and the category server data uses the same filters and card components as the client.
4. Recommendations and historical content can be mistaken for current authored research. Their URLs remain usable, while indexing directives and schema types distinguish their roles.
5. A semantic tag can change appearance through inherited CSS. Source review and full-page screenshot comparisons checked both themes and screen sizes.

## Search evidence and decisions

Google's [AI-search guidance](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) emphasizes normal crawlability, useful content, and search eligibility. It does not require special AI schema, fixed paragraph sizes, or llms.txt. The implementation therefore concentrates on accurate identity, initial HTML, meaningful links, and canonical consistency.

[ProfilePage guidance](https://developers.google.com/search/docs/appearance/structured-data/profile-page) supports a Person main entity for a personal profile. A company logo or Organization root entity would misrepresent this page. Google's [documentation updates](https://developers.google.com/search/updates) also record the retirement of FAQ rich results in May 2026; the scanner's FAQ demands do not justify adding visible material.

[Google Scholar inclusion guidance](https://scholar.google.com/intl/en/scholar/inclusion.html) recommends publication-specific metadata for individual paper/abstract URLs. One paper's citation metadata should not be attached to a homepage containing many papers. Existing paper destinations remain the authoritative publication pages.

Peer-reviewed results give reasons to avoid universal optimization formulas. Aggarwal et al.'s [GEO benchmark](https://doi.org/10.1145/3637528.3671900) reports domain-dependent gains, not a promised 40% improvement for this site or for FAQ schema. [SAGEO Arena](https://doi.org/10.1145/3770855.3818146) considers retrieval and reranking as well as generation and finds that rewriting can hurt earlier stages. [Wu et al.](https://arxiv.org/abs/2510.11438) report differing preferences across evaluated models and domains. These findings support accurate, useful information rather than keyword or statistics padding.

For Chinese discovery, the existing Chinese name and language signals are made consistent in metadata and the machine-readable summary. No translated page or hreflang pair is declared because the owner requested no new visible pages. [Google's multilingual guidance](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) applies if a maintained translation is requested later.

### Conclusions that affect implementation

1. The recurring defects are absent JSON-LD, weak section semantics, missing form labels/navigation aids, and missing security headers. Fix these in source and verify generated HTML and response headers.
2. Model the person as `Person` within `ProfilePage`, not as a company. Use known identity, affiliation, publications, and linked profiles. Do not invent credentials or publication dates.
3. Several warnings are demonstrably false or irrelevant to this site. A fresh request negotiated HTTP/2 and Brotli, downloaded 18,997 bytes, and had 0.112s TTFB. The first lazy image is an 18px navigation icon. The actual profile thumbnail is already preloaded. The two blank-alt images repeat a photograph inside a dialog whose accessible name is its visible caption. The current HTML contains one document title and an empty framework `noscript` marker.
4. Reports mostly scan the homepage. Their passing canonical and language checks do not establish correctness of posts, categories, or translated pages. `_document.tsx` currently fixes canonical and `og:url` to the homepage across every route; it also fixes `lang=en` while some article content is Chinese and sets `og:locale=zh_CN` on the English homepage. These are larger issues than several reported warnings.
5. Report scores measure their rules, not search visibility or citation probability. No supplied evidence establishes a 40% gain from FAQ schema, a universal preference for FAQs by any answer engine, or that all training crawlers must be allowed to appear in search answers.

### Foreseeable defects beyond homepage scans

- `_document.tsx` sets the homepage canonical and og:url globally. Metadata in next/document and next/head is not a reliable deduplicated shared metadata system. Use route-aware metadata with one title, description and canonical.
- Locale is inconsistent: English homepage, `og:locale=zh_CN`, fixed `html lang=en` for Chinese articles. A genuine Chinese profile requires its own crawlable URL, translated visible copy, reciprocal language alternatives, self canonical, and no forced locale redirects.
- `scripts/generate-static.mjs` currently lists posts only in sitemap, omits homepage and public indexes, and emits legacy `/friends` and category paths in llms.txt. Check every generated URL against real routes and exclude missing/duplicate content.
- Known profile links and Twitter card handle disagree. Use one identity source.
- Newsletter has duplicate submission paths via `onKeyDown`, submit, and button click. Client state alone may not prevent same-event duplicate requests. Use one submit handler, validate status, handle network failure and announce success/error.
- Footer returns null before mount. License/source/navigation content is absent from server HTML; only theme-specific controls need mount dependence. Footer back-to-top button is labelled 'change theme'.
- Header and Top use nested anchors/buttons. Replace with single native controls, retain focus states, and keep visible text as accessible names. Toolkit Button's default aria-label overrides meaningful child text.
- Current paper cards may use click handlers instead of paper-title anchors. Audit real hrefs for publications and preserve complete author/title/venue/year information.

### Evidence sources for policy decisions

- [Google AI features](https://developers.google.com/search/docs/appearance/ai-features) says standard SEO practices apply and no special schema is needed.
- [Google profile page guidance](https://developers.google.com/search/docs/appearance/structured-data/profile-page) specifies `ProfilePage` with the correct Person or Organization main entity and truthful profile properties.
- [Google documentation updates](https://developers.google.com/search/updates), May 8 and June 15, 2026 entries, records FAQ rich-result retirement and removal of its documentation. June 15 also clarifies llms.txt has no effect on Google visibility or rankings.
- Local Next.js headers and CSP documentation must govern framework-compatible headers. Do not copy the scanner's restrictive `default-src 'self'` blindly; this app loads analytics, remote images, inline hydration and styles.
